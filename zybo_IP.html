Zybo-Z7: Making and Adding a New IP

Start-to-end walkthrough for the Zybo Z7-10: package a brand-new AXI4 peripheral in Vivado, wire it into the block diagram, generate a bitstream, export the hardware, then bring it into Vitis Classic and read the IP's registers from C. Worked example: a simple free-running down-counter IP.

The full flow, at a glance:
  1. Open the project in Vivado
  2. Create and package a new AXI4 IP
  3. Point Vivado's IP repository at it
  4. Drop it into the block diagram and run connection automation
  5. Generate the bitstream
  6. Export the hardware platform (.xsa)
  7. Open Vitis Classic
  8. Import the new hardware / update the platform
  9. Find the IP's AXI base address
  10. Write the driver header/source and read the register from C
Step 1

Open the Project

Open "Vivado 2024.1" from your Xilinx Design Tools, then click "Open Project" (or pick one directly from "Recent Projects").

If you selected "Open Project," navigate through your HW folder to find the .xpr project file.

You're brought to the "Project Manager" page. Click "Open Block Design" under "IP INTEGRATOR" in the Flow Navigator sidebar.

Your previous block diagram opens up. To view the whole thing, click "Zoom Fit" or use Ctrl+0.

To find your Verilog, block diagram, and wrapper files, click on "Sources" in the top-left window of the Project Manager.
Step 2

Create a New IP

🌀 Variant: a multi-register IP with custom HDL (Lorenz attractor)Jump to the Lorenz IP walkthrough — same wizard, but with your own submodules and several live AXI registers instead of one

Navigate to Tools → "Create and Package New IP." Click "Next."

Select "Create a new AXI4 peripheral," then press "Next."

Type in a name for your block. If you don't have an "IP Location" already, Vivado automatically creates an ip_repo for you. Click "Next."

Your ip_repo is typically found in your hardware folder, but you can point it anywhere.

Edit your interface parameters as needed. Click "Next."

Select "Edit IP" to be taken immediately to the new hardware project containing your IP. Click "Finish."

If you want to import your own Verilog files instead of editing the generated sources in place, click the plus icon in the "Sources" pane to add them to the IP project.

Double-click {ip_name}.v in "Sources," and also {ip_name}_slave_lite_v1_0_S00_AXI.v:

  • {ip_name}.v — the direct connection to the AXI bus.
  • {ip_name}_slave_lite_v1_0_S00_AXI.v — a handshake FSM implementing the AXI bus protocol.

Implement your logic in the "...slave..." file, writing it out to the AXI data output. In this worked example, we create a free-running down-counter.

Leave slv_reg1–slv_reg3 in place as 0. Only slv_reg0 is replaced with a register named count_value.

Return to the main project: File → Project → Open or Open Recent. If prompted, click "Yes" to open the next project.

Step 3

Add the IP to Your Repository

In your main project, navigate to Tools → Settings (gear icon), then "IP" → "Repository."

Click the plus icon and find the folder named {ip_name}_{version_number} (e.g. down_counter_1_0). Click "Refresh All," then "Apply" and "OK."

If you've already pointed to the ip_repo in this project, the new IP may have been picked up already!
Step 4

Add IP to the Block Diagram

Right-click anywhere on the block diagram, click "Add IP...," and type in your IP's name.

A green bar appears at the top of the Diagram tab. Click "Run Connection Automation" to wire the pins.

If your AXI bus doesn't have enough ports, that's fine — automation creates a new Master port, clock, and reset for the peripheral.

In the popup, make sure all checkboxes for the IP are checked, then click "OK."

The AXI bus expands. Click "Regenerate Layout" to make the connections easier to see.

Step 5

Generate Bitstream

Automatically runs Linting, Synthesis, Implementation, and Place and Route.

Right-click in the block diagram whitespace and select "Validate Design." Hopefully no errors.

In the Flow Navigator, click "Generate Bitstream" under "PROGRAM AND DEBUG." Save if prompted, click "Yes" to run synthesis and implementation first, and set the number of jobs your machine can handle.

Track progress in the "Design Runs" tab. When complete, you'll see a completion popup — select whichever option and click "OK."

Synthesis is fast on cached IP blocks; new blocks take longer. A design not meeting timing isn't always a dealbreaker, depending on context.
Step 6

Export Hardware

Navigate to File → Export → Export Hardware. Select "Include Bitstream."

A bitstream is exactly how we configure the logic on the FPGA to make the hardware happen.

Name it whatever you want, click "Next," then "Finish."

Step 7

Open Vitis

Open Vitis and navigate to the appropriate workspace. Click "Launch," then "Continue With classic Vitis."

Step 8

Import the Hardware into Vitis

You're opened up to the Vitis workspace. Find the green icon — here it's named design_1_wrapper. Right-click it and select "Update Hardware Specification."

Click "Browse," find the .xsa file you just exported, then click "Ok."

Your hardware will show as (Out-of-date) — that's fine, it's fixed by building.

You must build to load in a MACRO to easily access your new AXI address.

In the Assistant panel, right-click "Debug" within the [Application] and click "Build."

Step 9

Find the AXI Address

In the "Explorer" tab, expand the hardware dropdown and double-click platform.spr. Click on "Hardware Specification" at the bottom left.

Scroll down the "Hardware Specification" page to see your IP's new address in the Address Map table.

Step 10

Read the IP from C

Create a new folder in src named after your IP (right-click src → New → Folder), then add a .h and .c file inside it (right-click → New → File).

Example .h file contents:

#ifndef DOWN_COUNTER_H_
#define DOWN_COUNTER_H_

#include "xil_types.h"

/*
 * Reads register 0 of the down_counter AXI4-Lite IP: a value that
 * decrements on its own inside the FPGA fabric, once per AXI clock,
 * from 1000 down to 0 (see count_value in
 * down_counter_slave_lite_v1_0_S00_AXI.v).
 */
u32 DownCounter_Read(u32 baseAddr);

#endif /* DOWN_COUNTER_H_ */

Example .c file contents:

#include "down_counter.h"
#include "xil_io.h"

#define DOWN_COUNTER_REG0_OFFSET 0x0

u32 DownCounter_Read(u32 baseAddr)
{
    return Xil_In32(baseAddr + DOWN_COUNTER_REG0_OFFSET);
}

Somewhere at the top of your main C file, add this line:

#define DOWN_COUNTER_BASEADDR XPAR_DOWN_COUNTER_0_S00_AXI_BASEADDR

Verify the address macro is proper by finding xparameters.h in the right-hand "Outline" column and double-clicking it. Search for your IP.

If you can't find it, cancel out of the tab, build the project, and open it again.

Example use of the code to read and print to the serial:

u32 countVal = DownCounter_Read(DOWN_COUNTER_BASEADDR);
xil_printf("down_counter = %lu\n\r", (unsigned long) countVal);
That's it — your new IP is packaged, wired into the fabric, exported, and readable from C on the Zybo Z7-10.
Step 11

Build and Run

Use the Application dropdown in the bottom-left corner of Vitis and select "Build and run."

There's often a JTAG/board-recognition error, or some other error, the first time you flash the board. Ignore it and just try again — it usually connects fine on the next attempt.
Variant

Lorenz Attractor IP: Multiple Registers & Custom HDL

This variant packages a real numeric solver — a fixed-point Lorenz-attractor ODE integrator — into an AXI4-Lite peripheral with three live registers (x, y, z) instead of one static counter. Steps 1, 3–9, and 11 above are identical no matter which IP you're building; only Step 2 (packaging/customizing the IP) and Step 10 (reading it from C) change, so this section only covers those two.

🔗 Full source on GitHublorenz_reader_1_0/hdl — the solver/integrator/multiplier HDL and the edited AXI wrapper files below, in full

Write the custom HDL first

Before opening the IP wizard, write your logic as ordinary Verilog/SystemVerilog sources and add them to your Vivado project like any other design source. For this IP that's three files: a signed fixed-point multiplier, a one-tap Euler integrator, and a top module wiring three of each into the Lorenz equations (dx = σ(y−x), dy = x(ρ−z)−y, dz = xy−βz), all in Q7.20 signed fixed point (27 bits: 7 integer bits including sign, 20 fractional).

// signed_mult.v — Q7.20 signed multiplier
module signed_mult (out, a, b);
    output     signed  [26:0]    out;
    input     signed    [26:0]     a;
    input     signed    [26:0]     b;
    wire     signed    [53:0]    mult_out;
    assign mult_out = a * b;
    assign out = {mult_out[53], mult_out[45:20]};  // re-align to Q7.20
endmodule
// integrator.sv — one-tap Euler accumulator
module integrator(out, funct, InitialOut, clk, reset);
    input                   clk;
    input                   reset;
    input signed [26:0]  funct;      // dV/dt
    input signed [26:0]  InitialOut; // reset value
    output signed [26:0] out;

    reg  signed [26:0] v1;
    wire signed [26:0] v1new;
    wire signed [26:0] adder_out;

    always @(posedge clk) v1 <= v1new;

    assign adder_out = v1 + funct;
    assign v1new = reset ? InitialOut : adder_out;
    assign out = v1;
endmodule
The third file, solver.sv, instantiates three integrators and three signed_mults and wires them per the Lorenz equations above. It has no AXI awareness at all — it's a free-running numeric core with plain clk/reset/constant inputs and x_next/y_next/z_next outputs, which is what makes it easy to drop into the wizard-generated wrapper in the next step.

Step 2 (Lorenz version): package the IP

Run the same wizard as Step 2 above (Tools → Create and Package New IP → Create a new AXI4 peripheral). When you get to "Edit IP," add your three HDL files to the IP project via the plus icon in "Sources," alongside the generated {ip_name}.v and {ip_name}_slave_lite_v1_0_S00_AXI.v.

Naming gotcha: get the IP's name right when you create it. If you rename the IP afterward (Package IP → Identification tab), Vivado renames the top-level wrapper file/module to match, but not the already-generated AXI slave submodule filename — so you can end up with a mismatch like lorenz_reader.v instantiating lorenz_reader_slave_lite_v1_0_S00_AXI.v (a leftover from an earlier working name). It still works fine, it's just confusing later.

In {ip_name}_slave_lite_v1_0_S00_AXI.v, add one port per solver output in the wizard's // Users to add ports here slot — this is the one sanctioned spot in the port list to touch:

// Users to add ports here
input wire signed [26:0] x_next,
input wire signed [26:0] y_next,
input wire signed [26:0] z_next,

// User ports ends

Latch those values into registers. This isn't a marked slot — just insert it in the module body, after the stock register declarations and before the stock AXI I/O assignments:

reg signed [26:0] x_reg, y_reg, z_reg;
always @(posedge S_AXI_ACLK) begin
  if (S_AXI_ARESETN == 1'b0) begin
    x_reg <= 27'sd0;
    y_reg <= 27'sd0;
    z_reg <= 27'sd0;
  end else begin
    x_reg <= x_next;
    y_reg <= y_next;
    z_reg <= z_next;
  end
end

Edit the register-read mux so each address returns the right signal, sign-extended from 27 to 32 bits:

assign S_AXI_RDATA =
    (araddr == 2'h0) ? {{5{x_reg[26]}}, x_reg} :
    (araddr == 2'h1) ? {{5{y_reg[26]}}, y_reg} :
    (araddr == 2'h2) ? {{5{z_reg[26]}}, z_reg} :
    (araddr == 2'h3) ? slv_reg3 : 0;
The easy-to-miss edit: this line is generated by the wizard and sits directly above the // Add user logic here marker — it is not inside any marked "Users to add" slot. The stock version just returns slv_reg0/slv_reg1/slv_reg2/slv_reg3 for the four addresses. If you only edit inside the commented slots, you'll miss this line and your registers will silently read back zero (or your leftover scratch values) no matter what your logic is doing. down_counter's AXI slave file has the identical edit at the identical spot, just returning one counter register instead of three.

In the top-level wrapper ({ip_name}.v), the wizard's own // Add user logic here slot near the bottom is not where this goes — your solver's outputs need to exist before the AXI submodule instantiation that consumes them. Instead, insert your constants and solver instance directly in the module body, right after the AXI port list closes and before that instantiation:

localparam signed [26:0] SIGMA = 27'sd10485760; // 10.0
localparam signed [26:0] RHO   = 27'sd29360128; // 28.0
localparam signed [26:0] BETA  = 27'sd2796203;  // 8/3
localparam signed [26:0] DT    = 27'sd8;        // 1/256 as a right-shift
localparam signed [26:0] X0 = -27'sd1048576;    // -1.0
localparam signed [26:0] Y0 = 27'sd104858;      // 0.1
localparam signed [26:0] Z0 = 27'sd26214400;    // 25.0

wire signed [26:0] x_next, y_next, z_next;

solver solver_i (
    .clk(s00_axi_aclk), .reset(~s00_axi_aresetn),
    .x_next(x_next), .y_next(y_next), .z_next(z_next),
    .x_0(X0), .y_0(Y0), .z_0(Z0),
    .beta(BETA), .sig(SIGMA), .rho(RHO), .dt(DT)
);

Then add three extra connections to the existing AXI submodule instantiation, one per solver output — the stock instantiation only wires up the 21 standard S_AXI_* ports, so this has to be added by hand whenever a custom port is added to the submodule below it:

lorenz_reader_slave_lite_v1_0_S00_AXI # (
    .C_S_AXI_DATA_WIDTH(C_S00_AXI_DATA_WIDTH),
    .C_S_AXI_ADDR_WIDTH(C_S00_AXI_ADDR_WIDTH)
) lorenz_reader_slave_lite_v1_0_S00_AXI_inst (
    .x_next(x_next),
    .y_next(y_next),
    .z_next(z_next),
    .S_AXI_ACLK(s00_axi_aclk),
    /* ...rest of the standard S_AXI_* ports, unchanged... */
);
A free-running fixed-point integrator with no periodic reset will numerically drift to (0,0,0) after tens of millions of cycles. If that matters for your use case, add a counter that pulses reset back to the initial conditions every few thousand cycles rather than leaving it fully unsupervised.

Continue with Step 3 through Step 9 above exactly as written — pointing the IP repository, adding the IP to the block diagram, running connection automation, generating the bitstream, exporting hardware, opening Vitis, updating the hardware specification, and finding the AXI base address are all identical regardless of which IP you built.

Step 10 (Lorenz version): read x/y/z from C

With three live fixed-point registers instead of one plain counter, the driver code needs to convert Q7.20 fixed point back to a float:

#ifndef LORENZ_H_
#define LORENZ_H_

#include "xil_types.h"

#define LORENZ_X_OFFSET 0x0
#define LORENZ_Y_OFFSET 0x4
#define LORENZ_Z_OFFSET 0x8

float Lorenz_ReadX(u32 baseAddr);
float Lorenz_ReadY(u32 baseAddr);
float Lorenz_ReadZ(u32 baseAddr);

#endif /* LORENZ_H_ */
#include "lorenz.h"
#include "xil_io.h"

/* Registers are 27-bit signed Q7.20, sign-extended to 32 bits in
 * hardware, so a plain signed 32-bit read already has the correct
 * sign - just divide out the 20 fractional bits. */
static float q7_20_to_float(s32 raw) {
    return (float)raw / (float)(1 << 20);
}

float Lorenz_ReadX(u32 baseAddr) { return q7_20_to_float((s32)Xil_In32(baseAddr + LORENZ_X_OFFSET)); }
float Lorenz_ReadY(u32 baseAddr) { return q7_20_to_float((s32)Xil_In32(baseAddr + LORENZ_Y_OFFSET)); }
float Lorenz_ReadZ(u32 baseAddr) { return q7_20_to_float((s32)Xil_In32(baseAddr + LORENZ_Z_OFFSET)); }
The driver files Vivado auto-generates ({ip_name}.h/.c/_selftest.c) are left as the stock template and never learn about x/y/z on their own — they still just define four generic register offsets. Either hand-edit those generated files, or do what's shown here: write your own small header/source pair in src (same pattern as Step 10 above) that reads the registers directly.

Finish with Step 11 above (Build and run) unchanged.
