Zybo-Z7 HDMI Driver: Git Cleanup & Synthesis Debug Log

How Zarif fixed the synthesis.

Overview

hdmi_driver/ is the Zybo-Z7 HDMI output-only project — HDMI input (RX) support was intentionally removed, leaving just the output path.

Important: Rule Out the Duplicate Wrapper Bug First

Check this before anything else. A duplicate top-level HDL wrapper was another reason synthesis kept breaking in this project — separate from the SyncAsync.vhd IP mismatch documented below. It's quick to rule out and easy to miss.
🐛 Duplicate Top-Level Wrapperzybo_bugs.html — "does not exist" errors from a stale HDL wrapper

Finding the Lorenz DDA IP

Asked where the "lorenz_dda" IP actually lives — it wasn't showing up under that name. The real name in the block design is lorenz_dda_driver (and there's an unrelated, differently-spelled axi_leronz_dda module floating around too — not the same thing).

A repo-wide search turned up many copies, because Vivado generates/caches an IP's source in several places per build:

find hdmi_driver -iname "*lorenz*"
hdmi_driver/Zybo-Z7-HW/Zybo-Z7-HW.ipdefs/repo/vivado-library/ip/lorenz_dda_driver_1_0/hdl/lorenz_dda_driver.v   # <- canonical source
hdmi_driver/Zybo-Z7-HW/Zybo-Z7-HW.gen/sources_1/bd/design_1/ip/design_1_lorenz_dda_driver_0_0/...                # generated copy
hdmi_driver/Zybo-Z7-HW/Zybo-Z7-HW.srcs/sources_1/bd/design_1/ip/design_1_lorenz_dda_driver_0_0/...                # generated copy
hdmi_driver/Zybo-Z7-HW/Zybo-Z7-HW.ip_user_files/...                                                                # generated copy
hdmi_driver/Zybo-Z7-HW/Zybo-Z7-HW.tmp/lorenz_dda_driver/...                                                        # stale scratch project
Rule of thumb for this project: the editable, canonical source for any packaged IP lives under Zybo-Z7-HW.ipdefs/repo/vivado-library/ip/<ip_name>/ — that's what "Edit in IP Packager" points at. Everything under .gen/, .srcs/, .ip_user_files/, and .tmp/ is a regenerated/cached copy that Vivado will silently overwrite. Never hand-edit those.

Diagnosing Synthesis/Implementation Errors

Two independent clusters of errors showed up on a build attempt:

Cluster 1 — synthesis, primary-unit collision:

[Synth 8-9871] overwriting existing primary unit 'syncasync'
  [".../ipshared/d57c/src/SyncAsync.vhd":61]

[filemgmt 20-1741] File 'SyncAsync.vhd' is used by one or more modules,
but with different contents, and may lead to unpredictable results:
* design_1_axi_dynclk_0_0 (.../ipshared/2a7c/src/SyncAsync.vhd)
* design_1_rgb2dvi_1_0    (.../ipshared/d57c/src/SyncAsync.vhd)

Cluster 2 — implementation, constraint/black-box cascade:

[Common 17-55] 'set_property' expects at least one object.
  [".../Zybo-Z7-Master.xdc":70]
[Vivado 12-4739] create_clock: No valid object(s) found for
  '-objects [get_ports hdmi_in_clk_p]'.
[Vivado 12-259] No clocks specified ... design_1_v_tc_out_0_clocks.xdc
[Project 1-486] Could not resolve non-primitive black box cell 'axi_dynclk'
[DRC INBB-3] Black Box Instances: Cell '.../axi_dynclk_0/U0' ... black box.

Traced cluster 1 to two Digilent IP cores — axi_dynclk and rgb2dvi — each bundling their own copy of a file named SyncAsync.vhd, with different contents:

diff ipshared/2a7c/src/SyncAsync.vhd ipshared/d57c/src/SyncAsync.vhd
6c6
< -- Date: 15 December 2017      # axi_dynclk's copy
---
> -- Date: 20 October 2014        # rgb2dvi's copy
64,65c64
<    kStages : natural := 2;
<    kResetPolarity : std_logic := '1');   # extra generic, only in the 2017 version
---
>    kStages : natural := 2);

Vivado's global/OOC synthesis merges same-named VHDL primary units across IP, so whichever copy loses the collision gets used everywhere — non-deterministic and exactly what "may lead to unpredictable results" warns about.

Traced cluster 2 to Zybo-Z7-Master.xdc still having an active HDMI RX pin/clock block (lines 69–81) referencing ports like hdmi_in_clk_p that don't exist on the top-level wrapper — confirmed dvi2rgb (the HDMI-input IP) isn't instantiated anywhere in design_1's block design:

grep -l "dvi2rgb" Zybo-Z7-HW.srcs/.../design_1.bd
(no match — not referenced in the BD)
This matched intent — HDMI input had been deliberately removed from this board to make it an output-only design. The stray RX constraints were leftovers from the original Digilent RX/TX reference XDC, not something missed.

Fix: commented out the whole HDMI RX block in Zybo-Z7-Master.xdc (pins + the offending create_clock line). That also resolved the downstream "no clocks specified" error on design_1_v_tc_out_0_clocks.xdc, which was just inheriting the missing-clock failure.

Root Cause: SyncAsync.vhd Mismatch

First attempt (wrong): misread the diff direction and copied rgb2dvi's (older, 2014) SyncAsync.vhd over axi_dynclk's. This broke synthesis differently:

[Synth 8-2043] formal port/generic <kresetpolarity> is not declared in <syncasync>
  [".../axi_dynclk.vhd":252]
[Synth 8-439] module 'design_1_axi_dynclk_0_0' not found
[Synth 8-6156] failed synthesizing module 'design_1'

That error made the real relationship obvious: axi_dynclk.vhd itself instantiates SyncAsync with the kResetPolarity generic —

SyncAsyncLocked: entity work.SyncAsync
   generic map (
      kResetTo => '0',
      kStages => 2,
      kResetPolarity => '0')   # axi_dynclk.vhd already expects the newer interface

So axi_dynclk's original bundled file (the Dec 2017 version, with the generic) was the correct one all along — it was rgb2dvi's bundled file that was the outdated mismatch. The earlier "overwriting existing primary unit" collision had been silently papering over this the whole time, because global synthesis happened to let axi_dynclk's correct copy win by luck of file-processing order — until it didn't.

Correction:
# restore axi_dynclk's original (correct) file from git history
git checkout HEAD -- ".../axi_dynclk/src/SyncAsync.vhd"

# propagate that correct file to rgb2dvi, which had the stale one
cp ".../axi_dynclk/src/SyncAsync.vhd" ".../rgb2dvi/src/SyncAsync.vhd"

Verified this was safe: rgb2dvi's own instantiation (in SyncAsyncReset.vhd) never sets kResetPolarity explicitly, so it just takes the new file's default value ('1'), reproducing the exact old behavior. Both files ended up byte-identical, correctly this time.

Regenerating IP Output Products

Editing the IP-repo source doesn't retroactively fix already-generated output products — Vivado needs to notice the repo source changed and regenerate. The generated copy under .gen/ kept showing the old content even after the repo-source edit, until this was done properly.

Also came up: axi_dynclk_0 doesn't appear as a flat top-level entry in the plain "Sources" view (it's nested inside the block design), so it's easy to think there's nothing to reset. Two reliable ways to reach it:

  • Tools → Report IP Status — flags any out-of-date IP (including ones nested in a block design), right-click → Reset Output Products → Generate Output Products (or Upgrade Selected first, if offered).
  • Sources panel → "IP Sources" tab — lists every IP instance flat, including ones buried in design_1.bd.
Do not try to "reset output products" on the top-level wrapper — it isn't an IP and has no output products of its own.

Sequence used: refresh the IP repo path (Settings → IP → Repository → refresh) so Vivado re-scans vivado-library, run Report IP Status, reset+regenerate the flagged IP (rgb2dvi_0 the second time around, since that's the one whose repo source changed last), then re-run Synthesis → Implementation → Generate Bitstream.

Synthesis succeeded after the corrected fix and a proper reset/regenerate cycle.

Vitis Classic: Missing Platform Project

Opening the hdmi_driver workspace in Vitis Classic to look at the C sources, the application project wouldn't open/resolve correctly. Inspecting the workspace's Eclipse metadata explained why:

ls hdmi_driver/.metadata/.plugins/org.eclipse.core.resources/.projects/
design_1_wrapper        # registered, but folder does NOT exist on disk
Zybo-Z7-10-HDMI_system  # registered, but folder does NOT exist on disk
Zybo-Z7-10-HDMI         # exists, has real source
RemoteSystemsTempFiles

And the app project's own .project file explicitly depends on the missing one:

<projects>
    <project>design_1_wrapper</project>
</projects>
The platform (design_1_wrapper) and system (Zybo-Z7-10-HDMI_system) project directories were never present on disk under hdmi_driver/. They were most likely deleted outside of Eclipse at some point (e.g. a manual folder delete) without Eclipse's workspace registry being told, leaving orphaned bookkeeping entries (marker files, resource-tree snapshots) behind for projects that no longer exist.

Planned fix (not yet executed — session ended here):

  1. In Vitis, right-click the ghost design_1_wrapper / Zybo-Z7-10-HDMI_system entries → Delete (clears stale metadata only; nothing real is on disk to lose).
  2. File → New → Platform Project, name it exactly design_1_wrapper (so the existing app-project dependency resolves), pointing at the freshly generated hdmi_driver/Zybo-Z7-HW/lorenz_ivan_9_18.xsa. Build it.
  3. Confirm Zybo-Z7-10-HDMI now resolves against the new platform (check C/C++ Build Settings if not).
  4. Fallback if the old app project shell still won't cooperate: create a brand-new Application Project against the new platform and copy the existing .c/.h files from Zybo-Z7-10-HDMI/src/ into it — the source itself is intact, only the project scaffolding is broken.
