I-03IP instance upgrade: stale definition / port-width warnings resolved

Symptom
ip_upgrade.log ends in CAUTION with IP_Flow 19-4706 (port width differs), 19-3374 (disabled parameter ignored) and Critical Warning Coretcl 2-1280.
Trigger
Report IP Status → Upgrade Selected on design_1_lorenz_dda_driver_0_0 after repackaging the IP.
How it was diagnosed
  • Log: Rev 1 → Rev 3, address ports 5 → 7 bits, disabled-parameter warning, Critical Warning.
  • The old instance came from the 7-register wizard version (WIZ_NUM_REG {7} → 5-bit bus). The Rev 3 Verilog has OPT_MEM_ADDR_BITS = 4 + ADDR_LSB = 2 = 7 bits for 12 registers.
Root cause

Nothing wrong: the register file grew, so the bus grew. The instance simply had to be upgraded.

Fix / workaround
  • Accept the 7-bit width; verify CONFIG.C_S00_AXI_ADDR_WIDTH = 7.
  • Re-check the address map (0x43C30000, 64K), validate, regenerate, re-synthesise, re-export the XSA.

I-06Vitis platform / BSP does not match the hardware resolved

Symptom
No LORENZ macro in xparameters.h; the Lorenz code is silently compiled out.
Trigger
Starting PS work with a platform still built from the Digilent XSA (dated 2024-07-04).
How it was diagnosed
  • xparameters.h dated 2024-07-04 with no 'lorenz'.
  • The app still built: Lorenz code is inside #ifdef XPAR_LORENZ_DDA_DRIVER_0_S00_AXI_BASEADDR, and the fallback only prints a hint.
Root cause

The BSP is generated from the XSA; it does not follow the Vivado project by itself.

Fix / workaround
  • Export the new XSA, Update Hardware Specification, Clean + Build the platform (also builds the BSP).
  • Confirm XPAR_LORENZ_DDA_DRIVER_0_S00_AXI_BASEADDR = 0x43C30000 and a current file date.

I-07Platform build fails in lorenz_dda_driver_v1_0 (Makefile typo) resolved

Symptom
gcc error: (ildcard: linker input file not found; then 'Failed to generate the platform' and cannot find -lrsa.
Trigger
Build Project on the platform right after Update Hardware Specification.
How it was diagnosed
  • gcc received the odd file names (ildcard and *.c).
  • Compared with the lorenz_reader driver Makefile, which is correct.
  • The -lrsa error is a consequence: the FSBL BSP never finished building.
Root cause

The generated driver Makefile has ($wildcard *.c); make expands $w as empty and leaves literal text.

Fix / workaround
  • Change to $(wildcard *.c) / $(wildcard *.o) (LIBSOURCES, OUTS).
  • Fix the source in ip_repo/.../drivers/.../src/Makefile and the six copies Vitis works from; re-export the XSA if the BSP re-extracts the bad one.
  • The repo also has lorenz_ip_hdmi/scripts/Convert-VitisMakefiles.ps1, which repairs these forms across an ip_repo.

I-14xil_printf has no %f; prompts missing on s resolved

Symptom
Pressing s shows no [value] prompts and nothing seems to update.
Trigger
New parameter-entry command.
How it was diagnosed
  • First version printed floats with xil_printf("%.4f") — not supported (garbage).
  • Switching to printf printed nothing: assistant's explanation was stdio buffering without a trailing newline on the bare-metal UART retarget (not separately verified).
Root cause

xil_printf lacks float formatting; printf output was not reaching the UART.

Fix / workaround
  • Format with snprintf into a string, print the string with xil_printf (same trick as the on-screen numbers).
Code · DemoPromptFloat — format floats with snprintf, print with xil_printf (C)
ivan_lorenz_hdmi/Zybo-Z7-10-HDMI/src/video_demo.c
static float DemoPromptFloat(const char *label, float current)
{
	char buf[32];
	char valBuf[16];

	/* xil_printf has no %f, and printf's buffering can swallow output with no trailing '\n' - so format via snprintf (proven to work) and print via xil_printf. */
	snprintf(valBuf, sizeof(valBuf), "%.4f", current);
	xil_printf("%s [%s]: ", label, valBuf);
	DemoReadLine(buf, sizeof(buf));
	if (buf[0] == '\0')
		return current;
	return (float) atof(buf);
}

I-16Plot clipped and slow resolved

Symptom
First run: trace crawled; plots looked cut off at the box edge.
Trigger
First working run of the plotter.
How it was diagnosed
  • Each displayed point advanced the solver by one Euler step of 2−10.
  • Redraw path flushes the whole 6.2 MB frame every point.
  • Apparent clipping was mostly the start transient and the monitor bezel; the axis ranges match the classic envelope.
Root cause

Tiny step per point plus a per-point full-frame flush.

Fix / workaround
  • 16 solver steps per plotted point; larger plot boxes; default delay 30 ms → 6 ms; +/- halve/double the delay.
  • A dirty-rectangle flush was written but dropped on purpose because it did not work as intended; the whole-frame flush stays and the speed is good enough.
Code · one plot update = 16 solver steps, read once, plot 3 projections (C)
ivan_lorenz_hdmi/Zybo-Z7-10-HDMI/src/lorenz_dda/lorenz_dda.c (lines 444-463)
/* Hardware steps performed per displayed point - batched so the trace doesn't crawl one tiny Euler step at a time, without touching dtShift or the PS-side redraw cadence. */
#define LORENZ_DDA_STEPS_PER_UPDATE 16u

void LorenzDDAPlot_Update(u8 *frame, u32 stride, u32 baseAddr)
{
	float x, y, z;
	u32 i;

	for (i = 0; i < LORENZ_DDA_STEPS_PER_UPDATE; i++)
		LorenzDDA_Step(baseAddr);
	LorenzDDA_ReadState(baseAddr, &x, &y, &z);

	PhasePlot_AddPoint(frame, stride, &plotXY, x, y);
	PhasePlot_AddPoint(frame, stride, &plotYZ, y, z);
	PhasePlot_AddPoint(frame, stride, &plotXZ, x, z);

	DrawCurrentValues(frame, stride, x, y, z);
}

I-18Stale BOOT.BIN / Create Boot Image fails resolved

Symptom
The only BOOT.BIN on disk was dated 2024-07-04; Create Boot Image errored.
Trigger
Making the design boot from SD.
How it was diagnosed
  • Debug/sd_card/BOOT.BIN is Digilent's old image (old app + bitstream).
  • Create Boot Image could not build its template because of the stale platform path (I-10).
Root cause

Stale artefacts from the archive plus I-10.

Fix / workaround
  • Fix the .sprj path, Create Boot Image → _ide/bootimage/BOOT.bin, copy to the SD root (JP5 = SD). Or run bootgen -image system.bif -o sd_card/BOOT.BIN -w.
  • Confirmed working: the FPGA runs the project on power-up.
