03.7Attempt 2: hang at the first Lorenz register write

What I did
  • Terminal showed [1]..[6] (HDMI, VDMA, capture all fine) and stopped after [6] plots cleared, writing regs.
  • Debugger Suspend: CPU in Xil_DataAbortHandler (cpsr = 0x600f01d7, abort mode), faulting str in Xil_Out32 → the first register write to 0x43C30000 got an error response.
  • XSCT: after fpga -file ...bit, mrd 0x43C30000 → Fault status 0x8, mrd 0x43C00000 OK → the running bitstream has no slave there.
  • Cause: the impl_1 outputs were from 18:15, before the BD repair at 18:46; the 18:49 bitstream came from a write_bitstream that only reopened the stale routed checkpoint. Earlier claims of 'timing met' were from that stale run.
  • Fix: reset_run synth_1, re-launch to bitstream, re-check timing, re-export XSA, Update HW Spec.
Why

A data abort (not a stall) on a PL address means 'nothing decodes it' — a bitstream problem, not a software one.

03.8Attempt 2: synthesis error, axi_dynclk is a black box

What I did
  • [DRC INBB-3] Cell 'design_1_i/axi_dynclk_0/U0' of type 'axi_dynclk' has undefined contents and is considered a black box.
  • Root cause, from Zarif's fix in commit f3a2572 for the same symptom: axi_dynclk.vhd instantiates SyncAsync with a kResetPolarity generic that rgb2dvi's older bundled SyncAsync.vhd lacks — a primary-unit collision, so axi_dynclk fails to elaborate.
  • Not fixed in place: I restarted from a fresh Digilent project once more instead (attempt 3) and it did not recur.
Why

Two IPs shipping different files with the same VHDL entity name is a library-version clash, not something to patch by hand in a fresh project.

Related: Issue I-13
