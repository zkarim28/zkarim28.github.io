I-01Vivado [Common 17-180] Spawn failed: No error resolved

Symptom
Eight identical 'Spawn failed: No error' messages when synthesising the custom IP.
Trigger
IP synthesis in the IP packager project, Vivado 2024.1 on Windows.
How it was diagnosed
  • Read the IP folder: no exec/spawn, no bad file references — the IP is clean.
  • TEMP and the project path were short ASCII. hostname printed Ivan??sLaptop.
  • Decoded $env:COMPUTERNAME in PowerShell: a code point 8216 (U+2018, curly quote) where the apostrophe should be.
  • Leftover scratch folders in git status were named .Xil/Vivado-700-Ivan’sLaptop/.
Root cause

Vivado creates .Xil/Vivado-<pid>-<host> for every run and spawns the run script there. A non-ASCII host name makes the OS-level spawn fail and GetLastError() is 0, hence 'No error'.

Fix / workaround
  • Rename the PC to plain ASCII (letters, digits, hyphen) and reboot.
  • Afterwards logs show Vivado-20976-IvanLaptop and the error is gone.
Code · check and fix the computer name (needs a reboot) (PowerShell)
$env:COMPUTERNAME
($env:COMPUTERNAME.ToCharArray() | ForEach-Object { [int]$_ }) -join ','   # any value > 127 is a problem (8216 = U+2018)
Rename-Computer -NewName "IvanLaptop" -Restart                        # plain ASCII, letters/digits/hyphen

I-03IP instance upgrade: stale definition / port-width warnings resolved

Symptom
ip_upgrade.log ends in CAUTION with IP_Flow 19-4706 (port width differs), 19-3374 (disabled parameter ignored) and Critical Warning Coretcl 2-1280.
Trigger
Report IP Status → Upgrade Selected on design_1_lorenz_dda_driver_0_0 after repackaging the IP.
How it was diagnosed
  • Attempt 1: the log said Rev 13 → Rev 1 and s00_axi_*addr 7 → 4 bits although component.xml was Rev 3 with a 7-bit bus. Zybo-Z7-HW.xpr had four overlapping ip_repo_paths, one to a deleted copy, so the catalog still held an old definition.
  • Attempt 3: log Rev 1 → Rev 3, 5 → 7 bits. The old instance came from the 7-register wizard version (WIZ_NUM_REG {7} → 5-bit address); the Verilog now has OPT_MEM_ADDR_BITS = 4 (5 index bits) + ADDR_LSB = 2 = 7 bits.
  • The instance property C_S00_AXI_ADDR_WIDTH is disabled in the packaged IP, so Vivado 'ignored' the attempt to restore the old value.
Root cause

Attempt 1: wrong catalog contents (stale repo paths). Attempt 3: nothing wrong — the register file grew from 7 to 12 registers, so the bus grew from 5 to 7 bits.

Fix / workaround
  • Set ip_repo_paths to exactly the two real repositories, update_ip_catalog -rebuild, confirm core_revision = 3 (vendor string is xilinx.com).
  • upgrade_ip; check CONFIG.C_S00_AXI_ADDR_WIDTH = 7; validate; regenerate outputs; re-synthesise; re-export the XSA.
  • Keep the 7-bit width. The Critical Warning is Vivado's generic message for any port change.

I-05Solver stuck at (0,0,0) resolved

Symptom
No software could make x/y/z leave zero (found by reading the RTL, before running).
Trigger
Planning the PS driver (attempt 1).
How it was diagnosed
  • In integrator.v the state loads InitialOut only while reset is active (reset = ~aresetn).
  • During reset the AXI registers, including x/y/z init, are zero, so the state always seeds to 0.
  • (0,0,0) is a fixed point of the Lorenz equations.
Root cause

Initial values could never reach the integrators.

Fix / workaround
  • Added a software load: CTRL bit 1 → lorenz_solver.load → each integrator: v1new = (reset | load) ? InitialOut : ....
  • Software: write params, CTRL=2, CTRL=0, then step. Edited without simulation; verified on hardware in attempt 3.
Code · integrator.v — accumulator with software load (Verilog)
ivan_lorenz_hdmi/Zybo-Z7-HW/ip_repo/lorenz_dda_driver_1_0/src/integrator.v
`timescale 1ns / 1ps

module integrator
(
input                   clk,
input                   reset,
input                   load,        // reload InitialOut without a global reset (software controlled)
input                   enable,      // pulse high for one cycle to take a single integration step
input signed [26:0]     funct,      //the dV/dt function
input signed [26:0]     InitialOut,  //the initial state variable V

output signed [26:0]    out //the state variable V
);

    reg  signed [26:0] v1 ;
    wire signed [26:0] v1new ;
    wire signed [26:0]  adder_out;

    always @(posedge clk) begin
        v1 <= v1new;
    end

    assign adder_out = v1 + funct;   // Adder
    assign v1new = (reset | load) ? InitialOut : (enable ? adder_out : v1); 

    assign out = v1; // Assign output

endmodule

I-14xil_printf has no %f; prompts missing on s resolved

Symptom
Pressing s shows no [value] prompts and nothing seems to update.
Trigger
New parameter-entry command.
How it was diagnosed
  • First version printed floats with xil_printf("%.4f") — not supported (garbage).
  • Switching to printf printed nothing: assistant's explanation was stdio buffering without a trailing newline on the bare-metal UART retarget (not separately verified).
Root cause

xil_printf lacks float formatting; printf output was not reaching the UART.

Fix / workaround
  • Format with snprintf into a string, print the string with xil_printf (same trick as the on-screen numbers).
Code · DemoPromptFloat — format floats with snprintf, print with xil_printf (C)
ivan_lorenz_hdmi/Zybo-Z7-10-HDMI/src/video_demo.c
static float DemoPromptFloat(const char *label, float current)
{
	char buf[32];
	char valBuf[16];

	/* xil_printf has no %f, and printf's buffering can swallow output with no trailing '\n' - so format via snprintf (proven to work) and print via xil_printf. */
	snprintf(valBuf, sizeof(valBuf), "%.4f", current);
	xil_printf("%s [%s]: ", label, valBuf);
	DemoReadLine(buf, sizeof(buf));
	if (buf[0] == '\0')
		return current;
	return (float) atof(buf);
}

I-16Plot clipped and slow resolved

Symptom
First run: trace crawled; plots looked cut off at the box edge.
Trigger
First working run of the plotter.
How it was diagnosed
  • Each displayed point advanced the solver by one Euler step of 2−10.
  • Redraw path flushes the whole 6.2 MB frame every point.
  • Apparent clipping was mostly the start transient and the monitor bezel; the axis ranges match the classic envelope.
Root cause

Tiny step per point plus a per-point full-frame flush.

Fix / workaround
  • 16 solver steps per plotted point; larger plot boxes; default delay 30 ms → 6 ms; +/- halve/double the delay.
  • A dirty-rectangle flush was written but dropped on purpose because it did not work as intended; the whole-frame flush stays and the speed is good enough.
Code · one plot update = 16 solver steps, read once, plot 3 projections (C)
ivan_lorenz_hdmi/Zybo-Z7-10-HDMI/src/lorenz_dda/lorenz_dda.c (lines 444-463)
/* Hardware steps performed per displayed point - batched so the trace doesn't crawl one tiny Euler step at a time, without touching dtShift or the PS-side redraw cadence. */
#define LORENZ_DDA_STEPS_PER_UPDATE 16u

void LorenzDDAPlot_Update(u8 *frame, u32 stride, u32 baseAddr)
{
	float x, y, z;
	u32 i;

	for (i = 0; i < LORENZ_DDA_STEPS_PER_UPDATE; i++)
		LorenzDDA_Step(baseAddr);
	LorenzDDA_ReadState(baseAddr, &x, &y, &z);

	PhasePlot_AddPoint(frame, stride, &plotXY, x, y);
	PhasePlot_AddPoint(frame, stride, &plotYZ, y, z);
	PhasePlot_AddPoint(frame, stride, &plotXZ, x, z);

	DrawCurrentValues(frame, stride, x, y, z);
}
