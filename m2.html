Altra-03 Optimization Results
ECE 6765 · team-03 · Milestone 2

Four optimizations, one win

Milestone 2 asks us to try four optimizations on the RAG pipeline. On altra-03 only one of them made queries faster. The reason is the hardware: the machine has one memory channel per socket, so 160 cores share about 26 GB/s, and generating an answer is limited by how many bytes each token has to read from memory.

The machine sets the limits

altra-03 is a two-socket Ampere Altra with 80 Neoverse-N1 cores per socket. The platform supports eight memory channels per socket, and each socket has one DIMM installed. That one fact explains most of what follows.

Three launches changed two of the answers

The first sweep ran each setup once. Two of those results did not hold up when repeated. The baseline itself varies by 5.6% from launch to launch, which matches the 6% Milestone 1 measured, so a single launch cannot resolve a difference smaller than about 12%.

Which stages got faster, and which got slower

A single total hides the trade. The pipeline logs the time of every stage for every query, so each change can be charged to the stage that paid for it. BF16 only touches generation, yet embedding and search moved by 8% and 13% in its runs. Changes that small are machine noise, so this table greys out timing changes under 15%.

Quantization: faster decode, slower queries

Why it did not help

BF16: the Neoverse-N1 cores have no BF16 instructions, so the library converts to FP32, computes, and converts back. That is more work than plain FP32. Decode hides the cost because it waits on memory; prefill pays all of it because it waits on arithmetic.

INT8: PyTorch's dynamic quantization re-quantizes the activations on every call and uses kernels built for batches. Decode handles one token at a time, so that overhead is never spread out. It also leaves the 620 MB vocabulary table in FP32, which is why the weights only halved instead of shrinking to a quarter.

What would make it work

The cores do have fast INT8 dot-product instructions (SDOT). Storing only the weights as INT8 or INT4 and using kernels written for one token at a time, which is what llama.cpp does, would cut the bytes per token by 4 to 8 times without the per-call overhead. That needs a new dependency.

Data parallelism: more waiting, little more throughput

What would make it work

Replication only pays once each replica is cheap. Quantization done properly would cut a replica's bandwidth use from about 64% to about 9%, leaving room for several. Better still is batching: decoding several queries' tokens together so one weight read serves all of them. Replicas copy the memory traffic; batching shares it. Today the generation service cannot batch, because its request takes a single query.

Approximate search: correct, but aimed at 0.7% of the time

What would make it matter

Search only matters if it becomes a bigger share of the query: a much larger corpus, a larger top-k, or generation becoming many times faster. Here its real value is memory. IVFPQ shrinks the 64-32 index from 1,694 MB to 61 MB, which on a 29 GiB machine frees room for another generation replica, at the cost of recall dropping to 0.56.

Chunking: spend 17 ms in search to save 508 ms in generation

This is a generation optimization that happens to live in the retrieval data. The 64-32 corpus has even shorter passages and should shorten prompts further, but it has not been measured end to end yet. It is the cheapest experiment left.

What it would take, in order

The four directions depend on each other. Treating them as separate checkboxes is how we got one win out of four. Each step below makes the next one possible.

  1. Weight-only INT8 or INT4 generationThe only change that reduces bytes per token, which is the only thing decode is waiting on. llama.cpp's kernels use the SDOT instructions this CPU has.
  2. Batched decodingOne weight read serves several queries. Needs the internal generate request to accept a list of queries; the public API stays the same.
  3. Then data parallelismOnce each replica uses a small share of bandwidth, several can run side by side.
  4. Approximate search for memory headroomA smaller index leaves room for those replicas, which is worth more here than the latency saving.
  5. Extend chunking to 64-32Independent of the rest, and the one direction already shown to work.

Limits of these results

  • Only short-query-answerable was measured end to end. The other three traces were not.
  • Data parallelism was run once. Its effect is far larger than the noise and every answer matched the baseline, but it has no error bars.
  • The top-down CPU counter analysis has not been run yet; it needs root.
  • With more than one query in flight, the per-service timing logs report negative transport times, so the stage split for data parallelism should be read as stage totals only.
  • These conclusions are about this machine's memory layout as much as the workload. With all eight channels populated per socket, the ridge would drop to roughly 5 FLOP per byte and the ranking could change.
